## 1. What authentication exists in the Go line

| Credential | Where | Notes |
|---|---|---|
| Bearer token (`Authorization: Bearer ...`) | `go/internal/auth/token.go` (`GenerateToken`, 32 bytes from `crypto/rand`, URL-safe base64, line 47; `TokenStore`; `subtle.ConstantTimeCompare`, line 96) and `go/internal/server/middleware.go:110-117` (`AuthMiddleware`); `rgt-vault init` (`go/cmd/rgt-vault/server_cmds.go:22-41`) | One static token for every caller. File on disk, 0600 in a 0700 dir (`token.go:73-76`). Read from the header only. The TUI (`go/internal/tui/client.go:177`) and the MCP bridge (`go/internal/mcp/mcp.go:328`) also send it as a header. |

Nothing else authenticates: no user accounts, passwords, password change/reset/recovery, hints, lookup secrets, OOB (SMS/e-mail/push), cookies or browser sessions, OAuth/OIDC/SAML/federation, FIDO/WebAuthn, OTP/TOTP verification, HMAC or challenge-response (greps in section 5).
The only TOTP code in Go is a countdown display in the TUI (`go/internal/tui/totp.go`); it verifies nothing.
The Go server is currently a skeleton (in-memory store, no per-agent identity, no approval broker); that is why some rows below are Gaps rather than Satisfied.

Python legacy, for reference only: the same bearer token model plus opt-in TOTP approvals (`python/totp.py`, `python/approval.py`), a double-submit CSRF cookie (`python/server/app.py`) and HMAC capability tokens. Its tests (`tests/test_totp.py`, `tests/test_server_approval.py`, `tests/test_server_hardening.py`) still exist but are not evidence for the Go line. `python/auth.py` is ABAC *authorisation* (ASVS V4), not authentication.

## 3. Accepted-risk statements (need human acknowledgement)

These issues stay open with `Refs`; a human must acknowledge each statement before they are closed.

**A1 (RGT-280, phishing-resistant authentication).** The Go line has one factor, a bearer token, which is neither phishing-resistant nor multi-factor; there is no second factor to phish. (The legacy Python line had phishable TOTP.) Context: the daemon is a local, loopback-intended service with no web login page to impersonate, and operators reach it through the CLI/TUI against a URL they configured. Residual risk: anyone who obtains the token file or a copy of the token can act as the caller. Mitigations: 0600/0700 file modes and no token in URLs (both guarded by tests). Running under a dedicated OS user is a deployment choice that is not yet scripted for Go (the existing `deploy/` scripts start the Python daemon). Closing this needs a hardware-bound or certificate-based factor (see A2) or a ported, per-agent identity design (RGT-236 batch).

**A2 (RGT-285, user-provided hardware authenticators).** U2F/FIDO tokens, smart cards and client certificates are not supported (G5: 0 hits in `go/`). Residual risk is as in A1. Revisit only if rgt-vault gains a multi-operator or remote-operator mode.

**A3 (RGT-315, verification keys in a TPM/HSM).** The only verification key in Go is the bearer token file, a plain file (0600 in a 0700 directory on POSIX, asserted by `TestTokenFileIsOwnerOnlyOnPOSIX`; Windows relies on the process identity because the test is skipped there). The master secret that will protect stored data has Argon2id/HKDF building blocks in `go/internal/kdf` but no TPM/DPAPI provider in Go yet (Python had `python/providers/`). Residual risk: anyone who can read the service user's files can authenticate.

## 6. Observations (nothing was changed in product code)

- **O1.** `python/email_verification.py` is dead code on the legacy line: imported only by tests (`tests/test_asvs_logging_crypto.py`, `tests/test_input_validation_epic.py`), cited by `docs/architecture/file-upload-policy.md`. It is not an authenticator. Deleting it is a human call (plan item N5); nothing was deleted.
- **O2.** The Go bearer token never expires and cannot be revoked per caller; rotation is replace-the-file-and-restart. All agents share one token (the identity gap covered by the B1 batch).
- **O3.** `rgt-vault init` (`go/cmd/rgt-vault/server_cmds.go:22-41`) overwrites an existing token file without confirmation and writes the token without a trailing newline, unlike `auth.TokenStore.Write` (which trims and adds one) and unlike Python's `init` (which refuses to overwrite). Follow-up: RGT-498.
- **O4.** `auth.LoadOrCreateToken` (`token.go:129`) returns whatever an existing file contains with no length or entropy check, so a short operator-supplied token is accepted. Follow-up: RGT-498.
- **O5.** The `rgt-vault --token` flag puts the token on the process command line, visible in `ps` to other local users; env var `RGT_VAULT_TOKEN` or the token file are safer (`go/cmd/rgt-vault/main.go:62`).
- **O6.** On a missing token file the auth middleware returns HTTP 500 with the file path in the JSON `detail` (`middleware.go`, `ErrTokenNotFound`); cosmetic information disclosure (also in RGT-498).
- **O7.** CORS in Go reflects any `Origin` when `CORS_ALLOWED_ORIGINS` is unset and `APP_ENV` is not `production` (`middleware.go:36-61`). Because auth is header-only and no `Allow-Credentials` is sent, this does not enable CSRF, but it is permissive (belongs to the V14 chapter owner).
