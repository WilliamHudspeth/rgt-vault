# ASVS 4.0: approval, TOTP and capability-token hardening (Go line, batch H2)

**Line of record:** Go (`go/`). The Python line is end-of-life and is not used as evidence.
**Verified against:** `origin/master` `8fabb53` plus branch `feat/h2-approval-2fa` (after the independent review of PR #56). Every verdict was checked in Go code and by Go tests run with `-race`. Older issue comments and older docs were not used as evidence.
**Review status:** Gemini review was unavailable (quota). An independent Claude security review of PR #56 found no critical or high defect; its medium and low findings are fixed in this branch (see "Review follow-ups" below).

Verdict key: **Satisfied** (`Closes`), **Partial** (`Refs`: part of the requirement is unmet), **Gap** (`Refs`, not met).

## What changed

| Area | Behaviour now | Code |
|---|---|---|
| Bad TOTP codes on `POST /v1/requests/{id}/approve` | Counted per request (cap 5: the request is **denied**, `DecidedBy` `system`) and per **operator identity** (its agent, so a second token of the same operator shares the budget; 10 in a **sliding** 5-minute window: the operator is **throttled**, 429 + `Retry-After`, and no code is checked, so a correct code is not consumed). A missing code counts like a wrong one. Every refused attempt writes `APPROVAL_BAD_CODE` (request id, token id, IP, `attempt=n/limit`, never the code). The operator table (1024 identities) fails closed: an unknown identity is throttled when it is full. | `approval.Broker.ApproveBy`, `CodeError`, `ThrottleError`; `handlers.reportApprovalFailure` |
| TOTP reuse | The server always builds the replay-guarded verifier. A reused code (same step, or an older step than the last accepted) is refused, written as `APPROVAL_CODE_REPLAY`, and sent to the notifier (log line, optional webhook). It is distinguished from a typo. | `totp.ReplayGuardedVerifier.VerifyResult`, `server.OpenStack` |
| Separation of duties | A request is pinned to the token that made it. A token cannot approve a request made with the same token id, and no token of the same agent can either. An approver that cannot prove an identity is refused. 403 + `APPROVAL_SOD_DENIED` + notification. Deny is always allowed. | `approval.separation`, `handlers.AuditHTTP` (`WithRequester`) |
| Request expiry | Unchanged and now tested through HTTP: after the timeout the agent gets a denial (`DecidedBy` `system`) and an operator can no longer approve it. | `Broker.lookup`, `Ticket.Wait` |
| `require_2fa` downgrade | A new version without `require_2fa` after a newest version (any status, a revoked one included) that had it is refused (403, `REQUIRE_2FA_DOWNGRADE_DENIED`) unless the token has the operator scope. The check runs in the same SQLite transaction as the insert. A permitted downgrade writes `REQUIRE_2FA_DOWNGRADED`. The legacy shared token never counts as operator for this. | `store.SetSecretChecked`, `vault.setSecret`, `handlers.SetSecret` |
| Approval for `set` / `rotate` / `revoke` | Opt-in: `serve --require-approval-for set,rotate,revoke` (or `all`; env `RGT_VAULT_REQUIRE_APPROVAL_FOR`). Default is none. Reads stay under `--require-approval`. Fields are validated and the per-agent rate limit applied BEFORE a request is parked; only requests the ABAC policy would allow reach the operator; the queue is capped (512 pending, 64 per agent by default; over a cap the call is a 429 and one coalesced `APPROVAL_QUEUE_FULL` row). `set` and `revoke` ask for a TOTP code when the secret has `require_2fa`; `rotate` when a TOTP secret is configured. | `approval.ParseGatedOps`, `handlers.gate` |
| Capability tokens | `serve --harness-key-file` now wraps the verifier in a replay guard: each token is accepted once until its own expiry. The token is consumed only after its agent, capability, version and bindings matched the request (a bystander cannot burn it). The cache is bounded, purged of expired ids on every accept, and refuses new tokens when full of live ids (it never evicts a live id). A replay is not counted as a failed credential. Replays are `CAPABILITY_DENIED` rows with `TokenReplayError`. | `captoken.ReplayGuard`, `server.OpenStack` |
| TOTP secret file | Created 0600 by the open call (`os.CreateTemp`, then moved into place; there is no chmod after the write). The server opens it once, checks mode and type on that descriptor (no stat-then-read gap) and refuses a file that group or others can access (POSIX). The last accepted time step is kept next to it (`<file>.state`, 0600, written before a code is accepted, keyed to the secret) so a restart does not reopen the replay window (RGT-510). | `cmd/rgt-vault/files.go`, `server.readTOTPSecret` |
| `enroll-2fa --force` | Needs an operator token when the token store has one. An explicitly named store (`--token-store` / `RGT_VAULT_TOKEN_STORE`) that is missing is an error. With no store, or one without an operator token, it is refused unless `--i-am-offline-operator` is given (the row then says `offline-ack`). Prints a warning and writes `TOTP_SECRET_REPLACED` with `old_secret_fingerprint` (first 8 hex digits of sha256 of the old secret) and the operator token id; refuses if the row cannot be written. This is a safeguard against mistakes, **not a security boundary**: whoever can write the 0600 file as the same user can replace it with any tool. | `cmd/rgt-vault/enroll.go` |
| Token mint / rotate / revoke / import | Each prints a `WARNING`, writes `TOKEN_MINTED` / `TOKEN_ROTATED` / `TOKEN_REVOKED` / `TOKEN_IMPORTED` (token id, agent, scopes, expiry, OS user; never the token), and sends the event to `$RGT_VAULT_SECURITY_WEBHOOK_URL` when set. If a vault exists and the row cannot be written, the new token is revoked again. | `cmd/rgt-vault/tokenaudit.go`, `token.go` |

Server-side notifications go to the log (always) and to a webhook (optional; set `RGT_VAULT_SECURITY_WEBHOOK_URL`: the `--security-webhook-url` flag is deprecated because a command line is visible in `ps`; loopback unless `--security-webhook-allow-remote`; netguard dial check, no redirects, no proxy). Delivery is bounded, with a separate reserved budget for lockout, auto-deny and self-approval events so a flood of ordinary events cannot hide them. Repeats of throttled / self-approval / queue-full events from one token are coalesced into one audit row and notification per 10 s with a `suppressed=N` count. Payloads carry the event name, request id, agent, token id and a short description; never a code, token or secret value (`TestH2*` `assertNoCode`, `TestCLISecurityWebhookNotifiesTokenAndTOTPChanges`).

## Audit events added

`APPROVAL_BAD_CODE`, `APPROVAL_CODE_REPLAY`, `APPROVAL_AUTO_DENIED`, `APPROVAL_LOCKOUT`, `APPROVAL_THROTTLED`, `APPROVAL_SOD_DENIED`, `APPROVAL_QUEUE_FULL`, `RATE_LIMITED` (gated operations), `APPROVAL_APPROVED`, `APPROVAL_DENIED` (also for a denied gated set/rotate/revoke), `REQUIRE_2FA_DOWNGRADE_DENIED`, `REQUIRE_2FA_DOWNGRADED`, `TOTP_SECRET_REPLACED` (now with fingerprint and operator), `TOKEN_MINTED`, `TOKEN_ROTATED`, `TOKEN_REVOKED`, `TOKEN_IMPORTED`.

## Operational notes

- **Approver of a gated rotation or a self-requested action** must be a different token *and* a different agent id than the requester. Mint a second operator token for another agent id (`rgt-vault token mint --agent ops2 --scope operator`).
- **Lockout is per operator identity** (its agent) and per request. Defaults: 5 bad or missing codes per request, 10 per operator in a sliding 5-minute window. `StackOptions.ApprovalCodeAttempts`, `ApprovalOperatorFails`, `ApprovalLockout`, `ApprovalMaxPending` and `ApprovalMaxPendingPerAgent` tune them for embedders; there is no CLI flag for them yet.
- **Operator state is in memory and bounded** (1024 identities). If the table is full of live entries an unknown identity is throttled (fail closed).
- **An honest operator who mistypes 10 codes is locked out for 5 minutes** (no admin override; the lockout ends by itself).
- **Webhook**: set `RGT_VAULT_SECURITY_WEBHOOK_URL` for both the CLI (token and enrol events) and the server. A dead webhook never blocks an operation; it prints or logs a warning (the URL is not printed because it may carry a key).
- **Behaviour changes to know about:** the agent token used as the operator token in legacy mode can no longer approve its own request; a `set` that omits `require_2fa` on a secret that has it is now refused for non-operators (send `"require_2fa": true`); a TOTP file with a group/other-readable mode is refused at startup on POSIX; **capability tokens are single-use** (see `docs/guides/migration.md`); `enroll-2fa --force` without an operator token to check needs `--i-am-offline-operator`; a missing code now counts as a failed attempt.
