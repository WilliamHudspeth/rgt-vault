# ASVS 4.0 V6 (Stored Cryptography) & V1.6 (Cryptographic Architecture) Verification — Go Line

**Line of record:** Go (`go/`). The Python line is end-of-life and is never used as evidence for any verdict below.
**Verified against:** `origin/master` (`e20fbf7`) plus this PR (`docs/h5-asvs-v6-go`); line references refreshed after merging that master (file:line refs drift — prefer the symbol names). Every claim below was verified directly in Go source files and exercised by Go unit/integration/AST tests — prior issue comments and older docs were not used as evidence.

**Scope:** 20 Multica issues (`RGT-243`, `RGT-244`, `RGT-245`, `RGT-393`–`RGT-402`, `RGT-404`–`RGT-408`, `RGT-220`, `RGT-221`).

> [!NOTE]
> **HTTP Server Wiring Status (transparent caveat):** On `origin/master` (`e20fbf7`), the Go vault core (`go/internal/{vault,store,keychain,crypto,kdf,captoken,totp,providers,audit,policy,validation}`) is merged and tested, while the HTTP server (`go/internal/server/handlers/handlers.go`) still uses its transitional in-memory stub store pending batch **G9** (and CLI `serve` wiring pending **G10**); no production package imports `internal/vault` (only `cmd/rgt-vault/cryptoaudit.go`, for two constants). All verdicts below are evaluated on the Go vault core and Go codebase; rows affected by pending G9/G10/H1/H2 work note that explicitly.

Verdict key:
- **Satisfied** — Verified directly in Go code and automated Go tests (`Closes RGT-n`).
- **N/A** — Requirement does not apply to `rgt-vault`'s scope, with evidence (`Closes RGT-n`).
- **Library-level** — Control is implemented and tested in the vault library, but no production code path (HTTP server) uses it yet (batch G9); deployment-level requirements are not closed on library evidence alone (`Refs RGT-n`; closes when the server runs on the vault, or when Will accepts library-level closure).
- **Accepted risk** — Requirement applies; control is partial with a documented residual risk requiring maintainer sign-off (`Refs RGT-n`).
- **Gap** — Requirement applies and Go does not yet satisfy all parts of it (`Refs RGT-n`).

## 3. Cryptographic Agility & Cipher Migration Plan (RGT-399 / D8)

### What agility exists today (no format changes)
1. **KDF parameter agility:** `keychain.json` persists `argon2_memory_cost`, `argon2_time_cost`, and `argon2_parallelism` (`go/internal/keychain/keychain.go:119-129`). `Manager.Load` reads the file's stored parameters (`keychain.go:237-240`), while `Manager.Initialize` and `Manager.Rewrap` accept upgraded `kdf.Params`. `RotateMaster` and `RotateDEK` re-wrap with `Config.KDFParams` (`rotate.go:156,274`), so a keychain is upgraded only if the embedding code passes stronger `Config.KDFParams`; no CLI flag or config file sets it today, and `cryptopolicy` does **not** feed it. Changing the params does not alter any secret ciphertext format.
2. **Strengthen-only crypto policy floors (`go/internal/cryptopolicy`) — audit-time check only:** Operators can write a YAML/JSON policy that raises minimum Argon2id memory/time/parallelism/salt floors and lowers DEK rotation ceilings, and `rgt-vault crypto-audit --policy ... --keychain ...` reports whether a `keychain.json` meets them. Policies can never weaken defaults or alter on-disk formats. The policy is **not enforced at runtime** (see "Policy wiring gap" below).
3. **Key rotation & versioning:** `Vault.RotateDEK` and `Vault.RotateMaster` replace keys atomically with epoch tracking (`metadata.key_epoch`), and `secrets.dek_version` (`go/internal/store/secrets.go:54-56`) provides per-row algorithm/version dispatch (`1` = AES-256-GCM; `0` = legacy Fernet, refused per D3).
4. **Token verifier abstraction:** `captoken.TokenVerifier` (`go/internal/captoken/verifier.go:12-18`) and payload `"v": 2` isolate callers from HMAC-SHA256 so asymmetric Ed25519 verification can plug in cleanly (RGT-35/RGT-46).

### Policy wiring gap (stated plainly)
- `cryptopolicy` is imported by exactly one production file, `go/cmd/rgt-vault/cryptoaudit.go`. `vault.Open`, `Vault.RotateMaster`, `Vault.RotateDEK`, `Vault.SetSecret` (DEK usage tally) and `keychain` never call `Policy.EffectiveKDFParams`, `CheckKDFParams` or `CheckDEKUsage`.
- KDF cost used when a keychain is created or re-wrapped comes from `vault.Config.KDFParams` (zero value = `kdf.DefaultParams()`); the DEK auto-rotation ceilings are the constants `vault.DEKMaxEncryptions` / `vault.DEKMaxBytes`. A policy file therefore cannot change either.
- Consequence: a keychain written with weaker-than-default params (for example the `KDFParams{1024,1,1}` the vault tests use for speed) is accepted by the vault; only `crypto-audit --keychain` would flag it.
- Closing the gap needs a follow-up that loads a policy in `vault.Config`/`serve`, applies `EffectiveKDFParams` in `Open`/`Rotate*`, and calls `CheckDEKUsage` where the usage counters roll over. Tracked by leaving **RGT-220**, **RGT-243** and **RGT-399** as `Refs`.

### Documented future cipher/algorithm migration plan (requires explicit sign-off)
Per **RGT-489** and **D8**, the secret ciphertext wire format (`nonce(12) || ciphertext || tag(16)`) and `keychain.json` v1 schema are frozen for byte-level Python↔Go compatibility and are **not** modified here. If a future cipher upgrade (e.g., XChaCha20-Poly1305, AES-256-GCM-SIV, or a self-describing version/algorithm header in ciphertext) is needed after Python removal (**GZ**):
1. **Explicit sign-off:** Open a dedicated follow-up issue/ADR for the format bump and obtain maintainer approval before changing any wire format.
2. **Versioned dispatch:** Increment `secrets.dek_version` (e.g. `dek_version = 2` for a versioned ciphertext envelope `[version(1B) || alg_id(1B) || nonce || ct || tag]`) and `keychain.json` `"version": 2` (checked strictly on load).
3. **Dual-read, single-write:** Support decrypting both `dek_version = 1` and `dek_version = 2` rows while writing new rows under `dek_version = 2`.
4. **Atomic migration:** Reuse the existing `Vault.RotateDEK` single-transaction `BEGIN IMMEDIATE` rewrite path (`go/internal/vault/rotate.go:214-314`) to re-encrypt every `dek_version = 1` row to `dek_version = 2`, bump `key_epoch`, and atomically swap `keychain.json`.
5. **Compat tests:** Pin golden vectors for both v1 and v2 formats before retiring v1 write paths.

## 4. Memory Hygiene & Residual Risk (RGT-408 / RGT-32)

- **Mitigations implemented in Go:**
  - The master secret is held by the OS/hardware key store at rest (`KeyringProvider`, `MacOSKeychainProvider`, `DPAPIProvider`, `TPMProvider`) and wiped via `defer keychain.Wipe(master)` immediately after KDF derivation (`vault.go:267`, `rotate.go:122,146,264`).
  - `Vault.Close()` and `keychain.Manager.Close()` overwrite the in-memory DEK slice with zeros via `keychain.Wipe` (`keychain.go:291-296`, using `runtime.KeepAlive` to prevent dead-store elimination), verified by `TestASVSV6_VaultCloseAndLeaseZeroizeKeyMaterial` and `TestASVSV6_KeychainCloseZeroizesDEK`.
  - `Vault.Lease()` wipes the decrypted secret plaintext slice in a `defer` block immediately after the caller's callback returns or errors (`vault/secrets.go:169-170`).
  - Windows DPAPI (`providers/dpapi_windows.go:36-39`) zeroes and `LocalFree`s the OS-allocated plaintext buffer before returning; Linux TPM (`providers/tpm.go:167,218-227`) zeroes and unlinks its 0600 scratch unseal file.
- **Honest residual risk:**
  - While a `Vault` instance is open, the 32-byte DEK lives in Go process memory as a heap `[]byte` (`Vault.dek`, `keychain.Manager.dek`) because AES-256-GCM runs in-process rather than inside an external HSM/PKCS#11 security module.
  - In Go, `keychain.Wipe` is **best-effort**: the Go runtime/garbage collector may relocate or copy backing arrays, stack frames are not wiped on return, `crypto/cipher`'s expanded AES round-key schedule is internal to stdlib, and `internal/kdf` Argon2id/HKDF intermediate buffers are garbage-collected rather than scrubbed (`keychain/keychain.go:49-51`).
  - Full hardware isolation (HSM/PKCS#11 crypto offload) or OS-level locked/non-swappable memory (`mlock`/secretmem/CGO enclave) is outside the current `CGO_ENABLED=0` Go threat model (see `docs/security/threat-model.md`) and is tracked under **RGT-32** (memory hygiene research).
  - **Maintainer action requested:** Explicit acceptance of this residual risk on **RGT-408** (or prioritization of RGT-32).
