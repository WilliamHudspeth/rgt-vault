# Release Security Gates

The release process for rgt-vault requires the following security gates to be green *before any tag is cut or any artifact is published*. This is in addition to the general release gate defined in `scripts/program/release_gate.py`.

These gates are additive — failure of any one of them blocks the release. No waiver is possible for `sev:blocker` issues; `sev:critical` issues require written Security Champion sign-off with an expiration date.

## Required gates

- [ ] **No open blocker issues** — `sev:blocker` count = 0 across all open tickets. Verified by `python3 scripts/program/release_gate.py --milestone <X>`.
- [ ] **No open critical security issues** — `sev:critical` AND `security:*` AND `status != done` count = 0. Verified by the same script.
- [ ] **Security review complete** — every ticket with a `security:*` label has `review:security` added during its lifetime (visible in ticket history, not just current labels).
- [ ] **Threat model current** — `docs/threat-model.md` was reviewed by the Security Champion within the last 90 days, and any architectural changes since the last review are reflected.
- [ ] **Dependency audit complete** — `pip-audit` (or equivalent) ran clean (no high/critical CVEs in the dependency tree); results posted to the release ticket.
- [ ] **Secret scanning clean** — `gitleaks` / `trufflehog` (configured in `.github/workflows/review-gate.yml`) ran clean against the full git history of the release branch.
- [ ] **SBOM generated** — a Software Bill of Materials (CycloneDX SPDX format) is attached to the release. Generated by `pip-cyclonedx-py` or equivalent, stored in `dist/sbom/`.

## Gate verification checklist

Before tagging:

1. Run `python3 scripts/program/release_gate.py --milestone <X>` and confirm "OVERALL: PASS".
2. Run the CI workflow (`.github/workflows/review-gate.yml`) against the release branch — all checks green.
3. Run `pip-audit -r requirements.txt` (or `uv pip audit`) locally; attach output to the release ticket.
4. Run `gitleaks detect --source .` and confirm zero findings.
5. Run the SBOM generation step (see `scripts/build_sbom.py` — to be created as part of v0.5.0 epic RGT-67).
6. Security Champion confirms gates 1–5 in writing on the release ticket.

## Rollback procedure

If a release passes these gates but a vulnerability is discovered post-release:

1. File a `sev:blocker` (or appropriate severity) ticket immediately.
2. The Security Champion coordinates the rollback / patch release.
3. The post-mortem (added to `AUDIT.md`) explains what gate was insufficient and how it will be tightened.

## Why these gates specifically

- **Blockers + critical security** — the obvious cases; a release with an open critical security defect is malpractice.
- **Threat model currency** — without this, "we did a security review" becomes "we did a security review 18 months ago" — a known failure mode.
- **Dependency audit** — most security incidents in modern codebases are upstream, not in the project itself.
- **Secret scanning** — catches credentials that landed in git history accidentally (and is cheap insurance).
- **SBOM** — increasingly required by customer procurement teams; also a forcing function for dependency hygiene.

## What this does NOT cover

- Penetration testing — that's a separate v1.0.0 gate (per `ROADMAP.md`).
- External security audit — also v1.0.0.
- Fuzz testing — v1.0.0 epic RGT-64.

These belong in v1.0.0 because the project does not yet have the test coverage to make them actionable.
